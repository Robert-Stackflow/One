# 全局热键占用进程定位方案

> 调研与首版实现日期：2026-10-08。范围：Windows 版 One 的快捷键冲突诊断。下文同时记录设计依据、当前实现和能力边界。

## 结论

可以把热键诊断器做成**按需启动、短时运行的独立原生进程**，在确有需要时仅提权这个进程；One 的 Electron 主进程、主窗口和文件拖放入口保持普通权限。微软也建议把需要权限的操作拆到独立辅助进程，而让主程序以 `asInvoker` 运行。[微软：管理员权限设计](https://learn.microsoft.com/en-us/windows/win32/secbp/running-with-administrator-privileges)

但“辅助进程以管理员身份运行”和“知道哪个进程占用了热键”是两件事。公开的 `RegisterHotKey` 只告诉调用者注册是否成功，失败时可取错误码，并没有列出已注册热键及其进程的查询接口。要给出有证据的进程名，应在组合键被触发时短暂观察目标进程收到的 `WM_HOTKEY` 消息。组合键可以由用户再次按下，也可以由诊断器在用户点击“自动测试”后用 `SendInput` 合成一次。此方案对使用 `RegisterHotKey` 的全局热键可行，对键盘钩子拦截、前台程序内部快捷键、Windows 保留键和受保护进程不能保证查到归属。[微软：RegisterHotKey](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-registerhotkey)、[微软：WM_HOTKEY](https://learn.microsoft.com/en-us/windows/win32/inputdev/wm-hotkey)、[微软：SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput)

## One 当前状态

- `src/main/index.ts` 的 `hotkeyConflict()` 已能区分 One 已知功能的快捷键，并尝试用 Electron `globalShortcut.register()` 判断某组合键能否注册。这个结果只有“可注册/不可注册”，不能据此断言是哪个外部进程；`isRegistered()` 只查询 **One 自身**的注册状态。[Electron 官方说明](https://www.electronjs.org/docs/latest/api/global-shortcut)
- `native/shortcut-capture.cpp` 用 `WH_KEYBOARD_LL` 捕获录入按键，捕获后返回 `1`，阻止按键继续传给后面的程序。因此在录入控件仍处于录入状态时，另一进程不会收到那次热键，诊断器也没有目标消息可观察。
- `src/main/shortcut-capture.ts` 已是独立原生辅助程序，但它仅负责**录入**，不能直接从该低层键盘事件推算最终由哪个进程接收热键。
- 当前“以管理员身份重新启动”会把整个 One 提权，设置页也已明确提示管理员模式下无法从资源管理器拖入文件。热键定位不应走这个入口。
- 原生构建脚本已能构建 x64 与 x86 辅助组件（例如对话框钩子），打包配置也有 `asarUnpack`。新诊断器可以沿用构建、打包模式，但须单独处理权限和生命周期。

## 方案比较

| 路径 | 能得到什么 | 主要不足 | 结论 |
| --- | --- | --- | --- |
| 注册探测：`RegisterHotKey` / Electron `globalShortcut.register()` | 判断 One 当前能否注册组合键 | 没有占用者 PID；失败也可能是系统保留键、无效组合等 | 保留作第一层判断 |
| 枚举进程或窗口，再猜测占用者 | 可展示常见热键工具的候选名单 | 不能证明这些进程注册了指定组合键，误报高 | 不作为“已定位”的证据 |
| 短时 `WH_GETMESSAGE` 钩子观察 `WM_HOTKEY` | 自动合成或用户按键后可得到实际接收消息的线程/进程 ID，再查询进程路径 | 要加载 DLL 到其他进程；需要 x86/x64 两套；不能覆盖非 `WM_HOTKEY` 的消费方式 | 推荐作为可选的“定位占用者”功能 |
| 长驻全局钩子、遍历并试按全部组合键 | 可能覆盖更多组合 | 侵入性、误触发、性能和兼容性风险明显 | 不采用 |

`WM_HOTKEY` 的 `lParam` 含修饰键和虚拟键码，因此钩子可以只记录用户正在诊断的组合键；`WH_GETMESSAGE` 可观察线程消息队列。微软说明全局钩子会影响同一桌面中的应用，必须及时解除；跨进程钩子过程必须放入 DLL，64 位 Windows 完整覆盖需要分别提供 32/64 位版本。[微软：WM_HOTKEY](https://learn.microsoft.com/en-us/windows/win32/inputdev/wm-hotkey)、[微软：SetWindowsHookEx](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowshookexw)

## 建议交互与进程边界

1. 快捷键组件先显示准确的状态：“One 内部冲突”“当前无法注册”“可注册”。“当前无法注册”旁提供“定位占用者”。不能把一次注册失败直接文案化成“某应用已注册”。
2. 点击“定位占用者”后，退出录入状态，停掉 `One.Shortcut.exe`，暂停 One 自己的相关全局快捷键。Electron 44 已有 `globalShortcut.setSuspended()`，但它会让暂停期间的新注册失败，故诊断流程不能再同时用注册探测；应先完成冲突判断，再进入诊断。[Electron 官方说明](https://www.electronjs.org/docs/latest/api/global-shortcut)
3. 启动普通权限诊断辅助进程，短暂安装 x64/x86 的 `WH_GETMESSAGE` 钩子。钩子确认就绪后，用户点击“自动测试”即可由辅助进程用 `SendInput` 合成**一次**组合键；也保留“手动按键”作为无法合成或目标忽略注入事件时的退路。若要覆盖管理员程序，再由这个**独立辅助进程**按需请求 UAC 提权；主窗口始终不提权。先确定钩子和权限是否可用，再发送按键；未收到结果时不得自动提权并重复发送。正式产品是否需要直接提权，需用 Windows 10/11 的普通与管理员目标进程矩阵验证后决定。[微软：SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput)
4. 钩子过程只比较目标键码并记录 PID/TID/时间，不读窗口内容、不记录任意按键、不执行磁盘或网络 I/O；将结果交给辅助进程后，由辅助进程查询进程路径。读取路径可用 `QueryFullProcessImageNameW`，失败时仍可返回 PID 与“路径不可读取”。[微软：进程路径 API](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-queryfullprocessimagenamew)
5. 普通权限 broker 建立当前登录会话内的共享内存并设置显式访问控制；短时运行的扫描器和注入目标进程的钩子只读写固定结构，不接受任意命令。broker 通过标准输出把结果返回 One。扫描器结束、取消或超时后，broker 退出并释放共享内存。
6. 得到结果、用户取消或超时后立即 `UnhookWindowsHookEx` 并退出诊断进程。恢复 One 自身快捷键注册及录入控件状态。钩子解除后，DLL 仍可能暂时被目标进程加载，因此升级/卸载时不能假设辅助 DLL 已立即可替换；不能直接把 Hotkey Detective 的实现或“关闭后可立即卸载”当作保证。[微软：钩子释放](https://learn.microsoft.com/en-us/windows/win32/winmsg/using-hooks)、[Hotkey Detective FAQ](https://github.com/ITachiLab/hotkey-detective)

### 结果文案

- **已定位**：显示应用名、PID、可读取的可执行文件路径，并注明“本次按键由该进程接收”。
- **未定位**：显示“当前无法注册，但未观察到 `WM_HOTKEY` 接收者”；说明可能是 Windows 保留、低层键盘钩子或其他系统处理。不要编造进程名。
- **诊断不可用**：区分用户取消 UAC、钩子安装失败、进程访问受限、超时及后台程序已退出。

### 自动发送组合键的条件与副作用

`SendInput` 可按顺序发送修饰键按下、主键按下/抬起、修饰键抬起。发送前要确保用户已经松开录入时按住的键，检查当前键态；无论发送结果如何，都只释放诊断器自己模拟按下的键。该 API 受 UIPI 限制：普通权限进程不能保证把输入送到管理员程序，且返回值不会明确报告“被 UIPI 阻止”。[微软：SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput)

对**确实到达 `WH_GETMESSAGE` 的匹配 `WM_HOTKEY`**，钩子可先记录接收进程，再将该条已取出的消息改为 `WM_NULL`，尝试避免接收程序执行热键操作；只应在本次自动测试的短时间窗口、确认 `PM_REMOVE` 后修改目标组合键的消息。微软文档明确允许 `GetMsgProc` 检查和修改 `MSG`，但仍须调用 `CallNextHookEx`。这一做法需要实际验证不同程序的兼容性，不能承诺完全无副作用。[微软：GetMsgProc](https://learn.microsoft.com/en-us/windows/win32/winmsg/getmsgproc)

低层键盘钩子能通过 `LLKHF_INJECTED` 识别模拟输入，可能主动忽略它；也可能在 `WM_HOTKEY` 出现之前就执行操作。Windows 系统快捷键或前台程序内部快捷键也可能发生可见动作。自动测试必须由用户点击触发，并直接说明“可能执行其他程序对应操作”；对锁屏、关闭窗口等明显有破坏性的组合键不自动发送，转为手动检查。不能为了定位而自动试按所有组合键，也不能一边吞键一边期待对方收到 `WM_HOTKEY`。[微软：注入键标记](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-kbdllhookstruct)、[微软：SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput)

## 实现阶段与验收

当前实现位于 `native/hotkey-probe.cpp`、`native/hotkey-probe-hook.cpp` 和 `src/main/hotkey-owner.ts`。所有快捷键录入组件共用一行简短冲突提示；“详情”弹窗提供进程名、PID、可执行文件路径以及“自动定位”“手动测试”。普通权限扫描无结果时，可显式选择“管理员范围”，仅提升扫描器，One 主进程仍为普通权限。自动定位只模拟一次组合键，已观察到的 `WM_HOTKEY` 会被改为 `WM_NULL`。这不能阻止低层键盘钩子或系统快捷键先发生作用，因此弹窗会提示自动测试的影响。32 位钩子未成功启动时，结果标记为覆盖不完整。

`tests/hotkey-probe-native.cjs` 使用临时编译的 64 位、32 位目标进程验证进程定位及消息抑制，也验证无人注册时返回“未找到”。管理员目标、Windows 保留键和低层钩子仍需用户在真实环境中验收；未观察到消息时绝不猜测进程。

1. **先修正状态语义**：明确 One 自身占用、注册失败、系统保留/原因未知。用现有 `hotkeyConflict()` 作为基础，不推断外部 PID。验收：内部冲突与外部不可注册的提示准确，录入不会卡住。
2. **原生诊断原型**：在独立进程中验证 x64/x86 `WH_GETMESSAGE`，只观察指定组合键、只运行一次。用自写的 x86/x64 测试程序分别注册热键，验证 `SendInput` 自动发送、接收进程 PID、单次消息抑制与手动按键退路；同时检查正常退出、取消、超时和用户已按住修饰键的情况。不得直接复制 [GPL-3.0 的 Hotkey Detective](https://github.com/ITachiLab/hotkey-detective) 代码进入 One，除非先完成许可证决策。
3. **主程序接入与按需提权**：实现一键诊断、权限不足时的独立 UAC 辅助、受限 IPC、日志和结果展示。验收：诊断前后 One 主进程权限不变；从普通资源管理器拖入文件仍正常；取消 UAC 不损坏快捷键状态。
4. **兼容性回归**：Windows 10/11，普通/管理员目标进程，x86/x64 目标，Electron/原生目标，Win 组合键、普通 Ctrl/Alt/Shift 组合键，以及低层键盘钩子型工具。对最后一类允许返回“无法确认”，不能误报其他进程。检查多次启动诊断后辅助进程不残留、快捷键可恢复、其他应用响应时间无明显退化。

## 风险与边界

- 全局钩子本质上会进入别的进程；即使钩子只做几条判断，也要做签名、超时、崩溃隔离与卸载测试。微软明确建议全局钩子只用于特殊用途或调试用途。[微软：SetWindowsHookEx](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowshookexw)
- 提权可以扩展诊断范围，但不等于可以观察系统所有进程；不同桌面、受保护进程和某些应用模型仍可能不可见。这个功能应标成“尽力定位”，不是保证找出任何热键的占用者。
- Hotkey Detective 是可行性参考：它也要求用户按下被占用热键，分别提供 x86/x64，且明确不识别浏览器这类仅前台有效的快捷键。其 DLL 卸载问题提示我们要把升级/卸载测试列为验收项。[项目自述](https://github.com/ITachiLab/hotkey-detective)
