# 文件索引内存与驻留

## 当前实现

约 431 万条真实记录的压缩快照约 79 MiB，加载成可修改的索引对象后，原生辅助进程私有提交约 923 MiB、工作集约 905 MiB。占用来自记录、排序结构、路径、匹配摘要及拼音等数据，并非磁盘缓存本身有 900 MiB。已有目录前缀共享与路径拼写压缩，仍不能消除每条记录的对象开销。

目前辅助进程启动时恢复完整索引，闲置期间保留它，以便检索、目录变化与增量验证复用。整份展开数据并非必须常驻；只保留目录监听、少量增量和查询缓存也能实现后台服务。直接闲置卸载当前对象会导致再次搜索重新恢复快照，同机实测约 5–7 秒，不能把它当成无代价的解决方法。

## 只读磁盘原型

原型与可修改索引共用查询解析、类型过滤、匹配分数、拼音与模糊匹配、目录优先级。独立诊断入口 `mapped-build` 只用于把验证副本转换为不可变镜像；`mapped-query` 每次查询映射只读镜像，返回前解除映射。活动应用没有启用这条路径，也不迁移用户缓存。

镜像按排序后的路径保存固定记录表，目录前缀共享，文字用相对偏移读取。可能性摘要与类型先过滤，再检查文字和拼音，避免对全部记录进行文字解码。当前目录通过二分查找直接定位子树，先交付局部结果，再扫描全局并合并前 100 项。

映射只允许读取，文件句柄拒绝同时写入；解析检查头部、节长度、偏移、UTF-8 和拼音数量。没有把 Rust 对象或指针直接持久化。接口依据：[CreateFileMappingW](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-createfilemappingw)、[MapViewOfFile](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-mapviewoffile)。

## 本机测量

固定验证 `mapped-index-performance` 使用同一份真实快照与增量日志的副本，关闭副本的扫描根目录，活动应用的配置及数据不变。原版、共用匹配代码的普通索引、磁盘原型分别使用新进程，每条查询重复两次，比较命中总数和全部前 100 项路径、名称、元数据、匹配类型。19 个条件包含拼音、模糊、引号、路径、类型、目录优先级及当前目录；全部结果一致。普通引擎的程序／设置过滤回归也通过，但磁盘原型尚未实现程序／设置混排。

首次对照样本为 4,315,595 条记录：

| 项目 | 可修改内存索引 | 只读磁盘原型 |
| --- | --- | --- |
| 闲置私有提交 | 约 923 MiB | 约 1.26 MiB |
| 闲置工作集 | 约 905 MiB | 约 5.02 MiB |
| 磁盘数据 | 压缩快照约 79 MiB | 未压缩镜像约 500 MiB |
| 仅恢复／打开索引 | 约 6.59 秒 | 约 31 ms |

原型镜像生成约 8.57 秒，仍先恢复旧快照，因此生成阶段没有解决高内存问题。31 ms 仅为打开已生成镜像，不包含首次转换、目录验证或监听初始化。

摘要预过滤后的全局查询墙钟约 0.15–1.01 秒，当前目录部分约 5–6 ms。与同轮普通引擎相比，有些查询更快，有些较慢：无结果约 252 → 150 ms，QQ 约 444 → 292 ms；广泛路径约 350 → 665 ms，拼写容错约 744 → 1,009 ms。测试按进程顺序执行，负载和调度存在波动，不能宣称固定速度收益。

解除映射后的空闲内存很低，但搜索中工作集峰值约 503 MiB；磁盘页还可能留在 Windows 文件缓存中，并非整个系统只使用 1 MiB。磁盘缓存因镜像刚生成而较热，本实验不代表重启后的冷存储读取。未通过强制清空工作集、减少记录或减少返回结果制造降幅。

首次原型没有摘要预过滤，全局查询约 0.55–0.98 秒，少命中场景明显较慢。两次实验的原始结果保留于有上限的验证目录，快照副本、镜像和测试配置结束后清理。

## 后续原型与运行版验证

第二版镜像把拼音偏移表与纯 UTF-8 文字池分开，拼音表按需借用，不再为每条候选记录分配数组。当前目录范围先逐段验证并返回结果；随后一次检查完整文字池，再在全局扫描中检查各片段边界。提前检查整池曾把局部响应拖慢至约 70 ms，已经撤回该顺序。只读文件句柄与偏移、文字边界检查继续保留。

诊断查询改为独立工作线程，输入线程持续接收新请求；每个搜索窗口拥有独立序号，过时查询每 1,024 项检查取消。20 次快速输入的测试有 19 次被取消，最后查询正常完成；独立窗口互不覆盖，过长条件返回错误后仍可继续检索。退出或输入关闭时释放映射并等待工作线程结束。

`mapped-scan-performance` 在同一份 4,316,642 项真实快照及增量副本上，前后原型交错运行两轮、各检查 18 个条件；总数、完整前百项与局部结果一致。第二版空闲私有提交约 1.26–1.31 MiB、工作集约 5 MiB，当前目录首批约 5–6 ms。广泛路径查询约 627–747 → 498–527 ms；少命中查询因完整文字池验证反而更慢，例如无结果约 161 → 276 ms。两轮聚合通过响应门槛，但并非每种查询都提速。镜像字节数保持相同，搜索工作集峰值仍约 500 MiB。样本仍使用热磁盘缓存，未测冷存储读取。

运行版另采用有上限的父目录匹配复用：每次路径查询仅保留最近一个父目录的判断，普通文件名继续走原匹配逻辑。`search-path-performance` 固定两个版本的测试辅助进程到同一逻辑处理器，对同一份 4,316,606 项快照交错测量两轮，每个查询两次，包含 18 类条件、程序／设置结果及查询取消；全部结果一致。两种分隔符的广泛路径查询约 334–340 → 265–268 ms，CPU 约 324–332 → 254–258 ms；常规查询有快有慢，逐项与聚合回退检查通过。测试固定处理器仅影响隔离辅助进程，活动应用的调度设置不变。私有提交仍约 925 MiB，此项并未解决常驻内存。

21 项 Rust 测试通过，另有一项诊断测量默认忽略；真实缓存的目录优先级、当前目录渐进结果和实际搜索窗口回归通过。开发实例经正常更新换用路径优化，管理会话保持运行；磁盘映射仍只用于诊断。

## 增量层与重启恢复

第三版诊断原型在不可变磁盘主体上叠加少量可修改记录。删除的主体记录用合并后的行号区间表示，删除大目录不必把其中每条路径放入内存；新增和修改项与主体按规范化路径顺序合并，继续复用原匹配器与前百项保留逻辑。普通查询和当前目录渐进查询分别与普通引擎的相同模式比较，不要求不同模式在同分候选中保留相同项目。

变更记录最多 20,000 项，删除区间最多 20,000 段，持久化增量文件最多 8 MiB。更新先在变更层副本上执行，成功写入并同步临时文件、替换旧增量后才确认；无效批次、容量溢出或写入失败保留此前确认的状态。主体新增 16 字节随机版本标识，防止相同行数和文件长度的新主体误用旧行号；头部填充使记录表维持此前的排列，镜像增加 64 字节。标识使用 [BCryptGenRandom](https://learn.microsoft.com/en-us/windows/win32/api/bcrypt/nf-bcrypt-bcryptgenrandom)。增量加载检查版本、校验和、长度、区间边界、重复路径及替换关系，损坏时报告错误并保留文件，尚未自动重建。

`mapped-overlay-performance` 使用同一份 4,318,430 项真实快照及增量副本，前后原型交错运行两轮，查询结果总数、完整前百项和局部结果一致，逐项及聚合 CPU 回退检查通过。当前目录首批约 4.5–5.8 ms；连续输入 20 次取消 19 次，独立窗口和错误后的恢复通过。墙钟受负载影响，不宣称固定查询速度收益，也未测冷存储读取。

隔离变更测试创建并重命名自有测试文件，再仅在缓存模型中模拟删除和重建一个含 16,475 条记录的目录，未删除真实目录。变更层保留 129 项记录、两个删除区间，最终 4,302,084 项，与加载相同变更的可修改索引一致。七类条件的普通和渐进模式均比较全部结果，重启后仍一致。

| 项目 | 测量值 |
| --- | --- |
| 129 项变更后的闲置工作集／私有提交 | 约 5.45 / 1.18 MiB |
| 相同最终记录数的可修改索引工作集／私有提交 | 约 904.6 / 926.4 MiB |
| 填满 20,000 项变更后的闲置工作集／私有提交 | 约 13.51 / 9.56 MiB |
| 变更分批提交过程的私有提交峰值 | 约 28.43 MiB |
| 搜索中的工作集峰值 | 约 505 MiB |
| 20,000 项变更的增量文件 | 约 2.01 MiB |
| 打开已生成主体并恢复 129 项变更 | 约 33 ms |

填充测试使用短 ASCII 路径，以上内存数值是该负载的测量，数量上限与文件大小上限不是同等的堆内存字节上限。33 ms 不包含首次生成、目录验证和监听初始化。暂存副本只复制变更层，未复制数百万条主体记录；满容量后的整批拒绝未改变已确认增量。24 项 Rust 测试通过，另有一项诊断测量默认忽略，覆盖目录边界、中文、大小写、删除重建、变更顺序、错误批次、持久化损坏及错误版本；普通引擎的真实缓存优先级和当前目录回归通过。

这一版本仍只用于隔离诊断，没有接入应用服务或目录监听。该阶段未包含后台合并，超出变更上限时明确要求合并；下一阶段的版本存储补上自动合并。主体的完整校验、损坏后的自动恢复和首次流式构建仍待完成。开发实例保持运行，运行版常驻索引的内存尚未因此下降。

## 流式后台合并与版本切换

新增隔离诊断入口 `mapped-store`，使用已生成镜像作为首次种子，在独立目录中持久化主体、增量及当前版本入口。主体与增量先分别保存完成，最后原子替换小型版本入口；此前确认的版本不受未完成输出影响。存储目录由专属标记和独占锁保护，拒绝使用无标记的非空目录，清理仅匹配自身生成文件名的普通文件。已发布版本缺少增量时明确失败，避免将缺失的已确认变更当成空增量。

合并线程顺序读取主体与变更的有序并集，逐项写入新镜像，不恢复可修改 `Index`。父目录复用表最多 32,768 项、路径文字预算 8 MiB，达到预算后清空复用表，允许镜像重复存储父目录；查询中的路径顺序与拼写不变。新记录、文字池、拼音表与最终文件分别流式写出，过程及复制阶段检查取消，生成文件继续受 1 GiB 上限约束。

生成期间搜索与更新使用旧版本。已确认的新变更另保留有上限的重放序列，发布前按原次序应用到新主体的增量，成功保存后才切换。重放数量或文字预算溢出时取消这轮输出，从最新已确认状态重试；写入错误保留旧版本，等待后续请求重试。数量上限与文字预算仍不等于严格的堆内存字节上限。

变更达到 4,000 项、删除区间达到 4,000 段，或主体被隐藏超过四分之一且至少 1,000 项时自动启动合并。启动时已积累到阈值的增量也自动继续合并，完成后如仍有大量新变更则继续下一轮。正常退出取消并等待生成线程；中途终止后仍按已发布入口恢复，清理未发布输出。旧主体与增量在成功切换后回收，避免每轮合并永久保留一个大文件。

`mapped-compaction-performance` 使用 4,318,238 项真实冻结快照。加入 127 项测试记录，后台生成期间再确认删除、重命名和新增，最终 4,318,367 项；20 个查询条件（含普通与渐进模式）分别与普通可修改索引比较，总数、完整前百项与局部结果一致。合并约 3.90 秒，私有提交峰值约 9.91 MiB，结束后工作集／私有提交约 5.96 / 1.45 MiB。父目录复用表在大索引上多次达到上限，未恢复主体的可修改对象。

合并中查询先返回当前目录结果约 7.15 ms，整个查询约 513 ms；同次实验未合并时首批约 4.6–4.7 ms、全局约 355–357 ms。后台写入仍会增加调度和 I/O 开销，不宣称全局无回退。合并与搜索并行映射文件，进程工作集峰值约 783 MiB，不能把低私有提交解释为整个系统只使用 10 MiB。

再确认 4,000 项短路径变更后自动启动合并，在观察到后台任务运行并完成一次搜索后终止隔离辅助进程。重启恢复最终 4,322,367 项，用准备好的主体与增量约 181 ms 进入可查询状态；此前所有 4,000 项变更仍可搜索，四个未完成节文件被清理。无需新更新或手动请求，后台自动重新合并约 3.35 秒；完成后变更记录及删除区间均为零，结果与中断前一致，目录只保留当前主体与增量两个版本数据文件，总计约 501 MiB。恢复及合并阶段私有提交峰值约 12.94 MiB，最终工作集／私有提交约 6.17 / 1.70 MiB，映射工作集峰值仍约 776 MiB。计时基于热文件缓存，不代表冷存储或任意路径长度的内存保证。

26 项 Rust 测试通过，另有一项诊断测量默认忽略。新增流式输出的逐项拼写、匹配摘要及拼音对照、取消不发布、版本发布失败保留确认状态、孤立版本清理及无种子重启验证；普通引擎真实缓存的目录优先级与当前目录渐进结果回归继续通过。活动应用没有切换后端，dev 管理器、主窗口与现有索引保持运行。

这一阶段原型仍需要已生成种子，`mapped-build` 依赖旧快照的完整内存恢复。下一阶段补上已有缓存的流式转换。上述恢复针对进程终止和文件发布中断，不代表已证明断电恢复或主体任意损坏后的回退。

## 已有缓存的流式转换

新增 `mapped-import`，只读解析现有快照和完整增量事务，复用缓存路径／元数据格式及记录恢复逻辑。排序快照按批次直接写出；旧格式允许的乱序快照使用有数量与文字预算的排序批次、16 路分层外部合并，不把全部记录装入内存。规范化后的重复路径继续拒绝，转换失败或取消保留原输出。源快照与增量文件不修复、不截断；不完整的尾部事务按旧读取规则忽略。

增量超过变更层容量时先把已接受变更流式折入中间主体，再继续后续完整事务，最终生成完毕才替换输出。转换与后台合并共用同一个镜像写入器，父目录复用表有上限；必要时追加未引用的父目录记录，使 64 字节记录表始终对齐。诊断命令集中分派，默认启动仍进入运行版服务。模块职责见[原生文件索引代码说明](../development/原生文件索引.md)。

`mapped-import-performance` 使用同一份 4,566,368 项真实冻结快照及 15 个完整增量事务。两种构建方式使用独立进程，查询辅助进程固定到同一个逻辑处理器，前后交错两轮，每个条件重复两次。19 类条件的总数、完整前百项与当前目录首批一致；源文件摘要不变，连续输入取消、独立窗口及错误后恢复通过。

| 项目 | 完整恢复后构建 | 流式转换 |
| --- | --- | --- |
| 构建峰值私有提交 | 约 1,092.8 MiB | 约 13.2 MiB |
| 构建峰值工作集 | 约 1,072.6 MiB | 约 553.5 MiB |
| 构建墙钟 | 约 12.3 秒 | 约 14.1 秒 |
| 镜像字节数 | 565,630,417 | 565,640,345 |

流式转换在折入旧增量时映射主体，仍产生较大的文件映射工作集，不能把私有提交降幅解释为整个系统只使用 13 MiB。查询结束后的工作集约 5.3 MiB、私有提交约 1.2 MiB，查询工作集峰值仍约 545 MiB；当前目录首批约 4–7 ms。聚合 CPU 约增加 3.8%，逐项及聚合回退门槛通过，但部分查询变慢，例如拼音首字母约 627 → 747 ms，普通目录条件约 312 → 350 ms；主要收益是降低构建内存，并非固定搜索加速。

28 项 Rust 测试通过，另有一项诊断测量默认忽略。包含 140,002 项乱序输入的多层外部合并、跨批重复路径、超过变更层容量的旧增量、中文与拼写／摘要／拼音逐项对照、损坏尾部及保留旧输出。共享写入器改动后，约 456 万项的后台更新、合并、中断恢复、自动继续和旧版本回收复测通过；普通运行版的目录优先级与当前目录渐进结果回归通过。测试使用热文件缓存，未测冷存储。

## 共用目录元数据与分批重新校验

新增 `FileCatalog`，内存索引和磁盘主体加增量共用单项查找、目录范围、直接子项与路径游标；磁盘读取只恢复当前选中的元数据，不恢复数百万条记录。运行版目录监听与离线校验的读取已经改用该接口，旧子项最多每批 512 项；离线校验每批最多检查 8,192 条记录，选中目录路径文字预算 4 MiB，检查后立即处理这一批变化，不再累计整份索引的所有变化。游标是路径，删除和替换子树后仍可继续。单目录枚举的已见集合与新增列表仍存在，不能称整个监听过程的暂存已全部有界。

`index-catalog-native` 冻结真实缓存，并在隔离模型中加入子项、大小写／类型变化及删除，最终 4,588,197 项。两种后端的 511,290 个目录、562 个响应包、完整游标、单项元数据、直接子项、普通和渐进搜索一致；原快照及增量摘要不变。System32 的 5,077 个直接子项分为十批，响应最大约 969 KiB。

磁盘版读取全部目录约 6.93 秒，内存版约 4.12 秒；磁盘每包平均约 10.2 ms、最长约 37.1 ms。磁盘辅助进程结束后私有提交约 5.14 MiB、峰值约 11.91 MiB，但文件映射工作集峰值仍约 551.2 MiB；包含约 1,537 条模型增量，不是整个应用的占用，也不是冷存储测量。逐包映射和解码仍有成本，不能据此宣称目录校验全面提速。

`index-reconcile-native` 使用自有的 9,000 个真实目录、1,800 个宽目录文件和范围边界样本。停止辅助进程后在各目录新增文件、重命名一个目录、删除 900 个文件，重新打开后约 1.0 秒恢复 18,903 项，所有新增文件可搜索；取消并继续、在线变化协议、宽目录两批读取、正常退出和持久化重启通过。这是约 1.9 万项的隔离负载，不能外推到 459 万项启动时间，也没有验证 JavaScript 监听器的 Windows 通知交付。30 项 Rust 测试通过，另有一项测量默认忽略，普通引擎优先级与当前目录结果回归通过。

## 接入前仍需完成

这不是运行版的常驻内存修复。共用的匹配、目录优先级、父目录复用及目录元数据接口已经用于运行版；原型的变更层、版本存储和后台合并仍需接到目录修改和应用搜索服务，还需主体快照校验与损坏恢复、版本迁移及程序／设置混排。独立查询取消已在原型中验证，尚未替代运行版服务。已有缓存转换已可流式执行，但无缓存首次文件系统扫描仍构建可修改索引，需要另外改造。

更合适的生命周期是磁盘索引持久化，搜索活跃期间保留必要读取和有上限的缓存，闲置后释放大数据视图，仅保留轻量监听和增量。正式接入前应验证实际后台负载、连续输入、冷存储响应、文件变更及内存上限。
