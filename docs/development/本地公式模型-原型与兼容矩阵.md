- Python 3.12.7 隔离环境位于 `work/current/capture-reconstruction/formula/.venv`；Paddle 3.3.1 和 3.1.1 均完成两次 CPU 推理。Paddle2ONNX 2.1.0 在 3.3.1 下遇到 DLL 加载失败，改为 3.1.1 后可运行；这是本机验证，不是全部版本的兼容承诺。[上游相同问题的版本说明](https://github.com/PaddlePaddle/Paddle2ONNX/issues/1615#issuecomment-3743495149)。完整依赖冻结见 work 中 `requirements-*.lock.txt`。

## 本机结果与边界

One 使用的 `onnxruntime-node` 1.30.0 直接加载修正图；CPU、DXGI 0（NVIDIA RTX 4060 Laptop GPU）和 DXGI 1（AMD 610M）每个后端两次推理，均返回 201 个 token。序列 SHA-256 全部为 `dfe5946933c02dd9f6345cb6ec30936c64b6463ce8678d9992f383e4f62c51a3`，与 Paddle 3.1.1 的序列一致；原生 ByteLevel 解码后的 LaTeX 相同，KaTeX 可解析。

| 独立原型运行 | 模型加载 ms | 首次/再次推理 ms | 进程峰值 RSS MiB |
| --- | --- | --- | --- |
| Paddle 3.3.1 CPU | 1807 | 2205 / 2047 | 570 |
| Paddle 3.1.1 CPU | 1723 | 2000 / 1813 | 563 |
| Python ONNX 1.31 CPU | 1394 | 679 / 675 | 767 |
| One Node ONNX CPU | 900 | 833 / 934 | 997 |
| One Node ONNX DirectML 0 | 1295 | 2028 / 941 | 1059 |
| One Node ONNX DirectML 1 | 1256 | 1935 / 1717 | 1028 |

最后一次 CPU token 严格校验与图文件散列并行运行，耗时 1301/1461ms；不把该次负载差异解释为模型质量或固定延迟。DirectML 原生事件分别记录 29964 次 GPU 与 28144 次 CPU 算子事件，确认有 GPU 执行，也不能宣传整图全部在 GPU 上或稳定更快。显存峰值尚未测量。这一官方印刷公式示例不证明矩阵、分段、多行、中文、手写、暗色或真实截图质量门槛通过。

当前以 CPU 作为 plus-S 默认后端候选，最终决定仍随完整样本和应用资源预算核验。转换后的模型超过现有 OCR 工作进程的 256 MiB 单文件限制；接入时需要独立公式任务契约及合理预算，不能直接解除 OCR 的既有边界。

## 可复现入口

1. 使用 `hf download PaddlePaddle/PP-FormulaNet_plus-S --revision 3d46f557e3a1752f4bf81202395af3b5ecfadfd2 --local-dir <work目录>` 取得固定文件；无需登录，下载时关闭隐式 token 使用。本轮仅下载 plus-S，其他尺寸未提前下载。
2. 在隔离的锁定环境中执行 [Paddle/ONNX CPU 探针](../../scripts/probes/formula-runtime.py)，必填 `--model-root`、`--image`、`--report`；ONNX 路线另传 `--onnx`。图像、权重、token 散列及资源记录写入 report。
3. 使用上述导出参数，然后执行标量修正脚本的 `--source`、`--output`。保留原始导出图，已有相同输出不重新写入。
4. [One 原生 ONNX 探针](../../scripts/probes/formula-onnx-runtime.cjs)接收 `--model`、`--sha256`、`--tensor`、`--config`、`--reference`、`--report`，支持 `--backend cpu/dml --device 0/1`。tensor 是 CPU 探针 `preprocess()` 返回的连续 float32 字节；reference 必须包含 Paddle 的 token SHA-256。每次使用新的 profiling 前缀，GPU 探针要求实际 GPU 事件，不能用旧日志冒充。

证据保留在 `work/current/capture-reconstruction/formula/`：官方版本元数据、权重、源图、依赖锁、原始/修正 ONNX、`plus-S-*.json/.log`、`scalar-repro.log`、原生设备映射和 profiling。应用接入后仍须验证安装准备、失败/取消、CPU 回退、设备/模型切换、独立窗口与退出；其他完整模型家族继续作为交付项。

## 独立公式任务运行层

`formula-local-runner.ts` / `formula-local-worker.ts` 已加入运行层和 worker 构建入口，未连接公共 IPC 或模型选择窗口。每个运行器拥有独立进程与热缓存；复用全局本地推理队列，切换任务所属运行器前卸载旧缓存。原图与模型身份冻结，回包必须匹配图片 SHA-256、模型/版本和后端；输入、设备或预算变化不能混用旧任务。Windows Job Object 默认限制 2048 MiB 进程提交内存，并在关闭句柄时结束进程；另采样 RSS。它不限制显存。取消、超时、错误和关闭等到实际进程退出才交还调度；仅自动模式允许同模型 CPU 回退，强制 GPU 错误不冒充 CPU 成功。

模型和字典按尺寸/SHA-256读取校验后的字节，拒绝文件链接，不在运行时再次按可变化路径加载。当前仅接纳已验证的 plus-S 图。预处理和推理都在子进程：PNG ≤8 MiB、解码 ≤4194304 像素、放大中间图 ≤8388608 像素；裁去空白后按 384 输入缩放/灰度归一化/补边。Node 预处理使用 sharp 的线性/三次重采样，不宣称逐像素等于 PIL；官方图与下列五组样本的识别文字已逐一与 Paddle 原预处理结果比较，一致。空白或过于狭长区域明确拒绝并保留输入。

按官方 `UniMERNetDecode.token2str`，只解码首次 EOS（2）及之前的 token；后续并行生成的尾部内容不属于公式。原型探针也已同步，raw token SHA-256仍记录完整模型输出。没有 EOS、字典/编码错误或无效字符不会交付假结果；不通过删除合法区间内的反斜杠“修正”模型。LaTeX 解析/语义质量仍独立验收。

`node tests/formula-local-runtime.cjs` 验证输入冻结、错误回包、GPU 回退/强制失败、取消、超时、硬内存限额、排队取消、其他任务启动前缓存卸载、实际 PID 退出、EOS/未知 token、空白输入；`--runtime` 使用既有固定模型检查真实 PNG→CPU 冷热识别，`--gpu` 检查 CPU→NVIDIA→AMD→CPU 切换，均不下载模型。`node tests/formula-case-images.cjs` 用本地 KaTeX 字体生成固定合成 PNG；`--runtime --cases` 记录逐个原文/识别文字及预览错误，不把语义错误当作后端失败藏掉。

| 合成样本 | 与 Paddle EOS 解码一致 | 本轮文字/结构观察 |
| --- | --- | --- |
| 分式/根式 | 是 | 主要表达式一致 |
| 矩阵 | 是 | 四项与括号保留，输出采用 matrix/left/right 结构 |
| 分段 | 是 | 条件与分段文字保留，但左括号有冗余 |
| 上下标/求和 | 是 | 主要表达式一致 |
| 多行 | 是 | 首行出现额外 c 与逗号，质量未通过 |

所有五组经 EOS 截断后可被 KaTeX 解析；这并不消除上述模型质量问题。样本是合成印刷公式，手写/中文/暗色/透明图和广泛真实截图仍待测，plus-S 尚不提升为默认公式模型。证据：`formula/local-{types,bundle,runtime,runtime-cases,runtime-gpu}*.log`、`local-case-results.json`、`cases/*-paddle-eos.json`、`local-runtime-result.json`。
