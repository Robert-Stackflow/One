# OCR、翻译、公式识别与截图采集重构

调研日期：2026-10-13。调研源码基线：`caa91ba`（0.16.24）。下文选型与模型效果属于调研结论，上游指标不等于本机结果；后续已开始实施，当前实现与验证状态统一见 [TODO](TODO.md)，原 Frame 迁移验收仍暂停。

## 1. 建议结论

| 范围 | 建议 |
| --- | --- |
| 普通 OCR | 本地优先，以 PP-OCRv6 small/medium 的官方 ONNX 模型为首选候选，与 v5 和当前 Tesseract 同样本比较后定默认档。复用已有 ONNX Runtime；不要求用户安装 Python。 |
| 图上选字 | 建立统一的图片文字几何数据和选择层，支持拖选、跨行、复制及局部翻译。不是给原图加一个全图文本框。 |
| 翻译 | 专用翻译服务适配器 + 现有 AI 服务；AI 仅选择已有服务/模型，不再填写另一套 AI 地址和密钥。 |
| 原图翻译 | OCR 分段 → 翻译 → 原文字区域处理 → 译文排版；优先保证文字和位置正确，再处理复杂背景。保留可编辑文字层和原图。 |
| 长截图 | 普通截图选区工具栏增加“长截图”，默认手动滚动自动采集，也支持自动滚动；两种模式共用采集、稳定检测和拼接引擎。 |
| 多窗口 | 优先重构为不可变快照：保存/编辑已经取得的像素不依赖源窗口继续存在；重新采集才检查实时窗口。 |
| 表格识别 | 删除专属入口、桥接和实现；保留普通 OCR 识别表格中的文字，不影响文件预览及已有表格工具。 |
| 公式识别 | 本地专用模型、SimpleTex 专用接口、现有 AI 视觉模型三种来源；本地支持多个模型家族及官方发布的不同尺寸，由用户选择，共用结果编辑和公式预览。 |

## 3. OCR 选型与图上选字

### 3.1 方案比较

| 方案 | 适用性 | 建议位置 |
| --- | --- | --- |
| Tesseract.js | 已集成、可离线、迁移风险小；当前使用的语言/版面配置有限。 | 保留作基准及兼容回退，是否长期保留由实测决定。 |
| PaddleOCR PP-OCRv6 | 官方已发布 tiny/small/medium；small/medium 覆盖 50 种语言，tiny 为 49 种且不含日文。官方提供 ONNX 模型。 | 优先评估 small 为默认、medium 为高精度；不能仅因 tiny 小就选为唯一引擎。[算法说明](https://github.com/PaddlePaddle/PaddleOCR/blob/main/docs/version3.x/algorithm/PP-OCRv6/PP-OCRv6.en.md)、[官方 ONNX 模型](https://huggingface.co/PaddlePaddle/PP-OCRv6_tiny_rec_onnx) |
| PP-OCRv5 / RapidOCR | 部署资料及 ONNX 推理路径成熟；RapidOCR 提供词级框输出，可参考前后处理和坐标还原。 | 与 v6 同测；RapidOCR 是部署工具，不是另一种独立识别模型。不直接假设其当前发布版完整支持 v6。[模型列表](https://rapidai.github.io/RapidOCRDocs/main/en/model_list/)、[词框输出](https://rapidai.github.io/RapidOCRDocs/main/en/install_usage/rapidocr/usage/) |
| PaddleOCR.js | 官方提供浏览器 SDK 和 Worker 用法，当前示例以 PP-OCRv5 为主。 | 原型比较其前后处理复用价值；不默认在主窗口线程推理，也不假设 SDK 与所有 v6 模型直接兼容。[官方部署文档](https://www.paddleocr.ai/latest/version3.x/inference_deployment/cross_platform/browser.html) |
| Windows AI Text Recognition | 系统能力有硬件/运行环境条件，当前官方支持表中该 OCR API 需要 Copilot+ NPU。 | 可作为未来增强，不能作为全用户默认依赖；不要与旧 `Windows.Media.Ocr` 混为一谈。[官方支持表](https://learn.microsoft.com/en-us/windows/ai/apis/) |
| 视觉大模型/云 OCR | 可补充困难图片与复杂版面，但有延迟、费用、上传和文字幻觉问题，坐标稳定性也需验证。 | 用户选择的增强来源；不静默上传，也不让模型猜出的文字冒充原图精准位置。 |

One 已有 `onnxruntime-node`、Sharp 和模型下载/校验能力。优先在独立推理 Worker 中运行检测、方向处理、识别和后处理，复用模型缓存；模型首次使用按需下载，记录版本、字典、前后处理配置、大小、哈希和许可，原子完成安装。代码许可和具体权重许可分别核对，不只看仓库首页。

首批原型固定 [tiny 检测](https://huggingface.co/PaddlePaddle/PP-OCRv6_tiny_det_onnx/tree/2ba1506c0380b8f0b03dd142459aac66d4421f6c) 与 [tiny 识别](https://huggingface.co/PaddlePaddle/PP-OCRv6_tiny_rec_onnx/tree/2612ab37152ae0a677521bae4e1e3d4fb4cf7c30) 官方 ONNX/YAML，权重许可标为 Apache-2.0；使用同版本字典和前后处理，不需要 Python。已实现 CPU/DirectML 推理、DB 文字框与透视裁剪。统一文字文档保留真实检测四边形；CTC 发射区间与高对比图片的墨迹列投影提供近似字级选择，扣除输入补白并还原透视、竖行旋转和行方向，缺失或不一致时保留原行框，不均分伪造字框。small/medium 已接入 0°/180° 行方向模型，tiny 不支持倒置行。推理已移入独立进程，校验后的权重字节直接交给 ONNX，避免校验与加载之间再打开可变化的文件；取消、超时和内存超限结束整个推理进程，旧输入保留。模型/设备入口和首批跨功能调度已接入，默认 OCR 仍为 Tesseract；真实文档质量、复杂版面阅读顺序与默认档仍待验收。

可重复基准入口为 `node scripts/prepare-recognition-benchmark.mjs --prepare` 和 `node tests/recognition-paddle-runtime.cjs`，前者无 `--prepare` 时只验证已缓存文件。当前通过 60 张合成单行与中英三行、深色、顺时针 90°、紧裁剪单行四类整图的 CPU/DirectML 设备 0 核验；同图 Tesseract 也识别出预期文字，因此不能据此证明默认引擎应替换。结果记录文字、CER、冷启动、阶段耗时和进程 RSS，GPU 峰值显存尚未测量；DXGI 设备号/会话身份与指定设备推理已核验，真实分层样本与其他模型/尺寸仍按 A 门槛验收，不把合成样本成绩推广到真实使用场景。

small/medium 已接入模型目录与实际推理，使用官方 [small](https://huggingface.co/PaddlePaddle/PP-OCRv6_small_rec_onnx)、[medium](https://huggingface.co/PaddlePaddle/PP-OCRv6_medium_rec_onnx) 与 [PP-LCNet 文字行方向模型](https://huggingface.co/PaddlePaddle/PP-LCNet_x1_0_textline_ori_onnx)，全部版本/大小/SHA-256 固定在 `local-model-catalog.ts`。官方方向预处理为 RGB、160×80 线性缩放与归一化，按 0°/180° 分类翻转真实透视裁剪行，不补造字符框。tiny 保留原四文件兼容入口。三档共计 14 份不同文件，`node scripts/prepare-recognition-benchmark.mjs --all-ocr` 只验证本地文件；显式加 `--prepare` 才允许准备缺失文件，支持 `--preset` 限定预设。

small/medium 各通过五组合成图像（英文、中英/邮箱、深色、180°、90°）的 CPU、NVIDIA 与 AMD DirectML 原型核验；不等于真实语料质量门槛通过。五组 CPU 进程采样峰值分别约 1126/2046 MiB，预设 RSS 预算为 1536/3072 MiB，显存仍未知；这些峰值是该组样本的测量值，不是最低配置要求。`node tests/paddle-presets-runtime.cjs` 通过固定缓存/哈希、缺失方向配置拒绝、实际倒置与深色混排、源图哈希/模型版本、租约、同预设热复用，以及 small→medium→small 切换；模型、设备或预算变化时先结束旧原生进程，再运行新任务，避免残留内存占用破坏较小预设的预算。`node tests/local-model-ui.cjs --presets` 验证从真实弹窗选择 small/medium、应用后关闭、正确版本与 medium 热运行预算。默认仍为 Tesseract，v5、其他模型和真实分层质量验收继续按 A 门槛推进。

识别界面按最新交互要求统一为图片编辑器式工作台：顶栏识别/缩放/旋转图标、底栏复制，图片与结果可拖动调宽，默认图片更宽且结果栏可完全收起。OCR 原文与翻译同时置于右栏；选中文字翻译保留原文。LaTeX 识别使用独立窗口、图片副本、preload/IPC 和资源授权，关闭 OCR 不取消公式任务。“OCR 模型”弹窗仅管理 OCR，采用左侧模型、右侧设备/资源的结构，删除移至模型标题栏；翻译/视觉服务设置按连接与身份验证分组。OCR/公式共用无滚动条的图片画布，普通滚轮锚点缩放、空白/空格/中键拖动；处理时显示不透明纯色遮罩，无进度条、磨砂效果或常驻提示条。图上选字操作条使用实色表面，两按钮中间直角衔接；顶栏移除重复的取消识别按钮。真实窗口回归已覆盖分栏/收起、图上选字、翻译、独立公式与退出/重新打开；完整模型家族及其他阶段仍按本计划验收。

### 3.2 本地模型、尺寸与 GPU 管理

本地能力采用可扩展模型目录，不只内置一个“最佳模型”。用户可以分别为 OCR、公式识别和原图翻译的背景修复选择模型、尺寸及推理设备；默认推荐档仅作为初始选择，不限制其他已适配型号。现有 AI 服务中的 Ollama/LM Studio 等仍由服务端管理其模型和 GPU，不把外部模型复制到 One 的模型目录。

模型选择至少覆盖：

| 用途 | 计划支持的模型及尺寸 |
| --- | --- |
| OCR | PP-OCRv6 tiny/small/medium；PP-OCRv5 mobile/server；DeepSeek-OCR v1/v2 Q8 已接入 Windows x64 原生 CPU/CUDA 文字识别，图上几何待补；保留 Tesseract 兼容入口。每个 OCR 预设绑定相容的检测、方向、识别模型与字典，不能任意混用。 |
| 公式 | PP-FormulaNet S/L、PP-FormulaNet_plus S/M/L、UniMERNet tiny/small/base，以及 pix2tex 官方实际发布的权重版本。不为没有发布尺寸的模型虚构 S/M/L。 |
| 图片背景修复 | 将现有 MI-GAN 纳入同一管理方式；只展示经过验证的权重版本/精度档，不伪造多尺寸选择。 |

DeepSeek 原生可行性已核验：官方 [v1](https://huggingface.co/deepseek-ai/DeepSeek-OCR) / [v2](https://huggingface.co/deepseek-ai/DeepSeek-OCR-2) 的 Transformers 示例依赖 CUDA/PyTorch/Flash Attention；本应用采用无需用户安装 Python 的原生运行包路线。llama.cpp 的 [v1 支持](https://github.com/ggml-org/llama.cpp/pull/17400) 与 [v2 支持](https://github.com/ggml-org/llama.cpp/pull/20975) 已合入上游，固定候选运行包为 [b11588 Windows x64](https://github.com/ggml-org/llama.cpp/releases/tag/b11588)，发布物大小与官方 SHA-256 已核验。本机原生 CUDA 包识别 RTX 4060；两个版本的 Q8 语言模型和视觉投影文件均已固定版本/大小/SHA-256，来自 [ggml-org v1 转换](https://huggingface.co/ggml-org/DeepSeek-OCR-GGUF/tree/7086620c3e417c744eb30dd3090fd053c6bb2e5e) 与 [v2 支持作者转换](https://huggingface.co/sabafallah/DeepSeek-OCR-2-GGUF/tree/d08e5af400c64fa8a9b89b04ba373b600b02e05d)，不将转换文件标为 DeepSeek 官方 GGUF。

两版分别通过原生 CUDA 英文和深色中英/邮箱合成图像，v1 进程启动至完成约 14.6/9.1 秒，v2 约 6.1/4.7 秒，语言层实际 13/13 卸载至 GPU。CPU 英文分别约 31.4/13.6 秒，已验证同模型 CPU 路线可用。Vulkan 包能枚举 NVIDIA/AMD，但 v1 的部分视觉算子回落 CPU，两段图像编码日志累计约 34.7 秒，不能据此宣传与 CUDA 同等加速。固定 GGUF 预设、运行包缓存、设备映射和后台推理/调度已接入 OCR 模型目录与窗口；两版可选择 CPU/NVIDIA CUDA，应用时自动准备运行包与权重，无需用户配置 Python。真实文档质量与图上几何仍待验收。权重验证与原型日志保存在 `work/current/capture-reconstruction/deepseek`，后续复用，不重复下载。

原生运行包由 `LlamaRuntimeStore` 单独管理，不加入安装器或模型侧栏。CPU 包固定 31 份文件，CUDA 包连同依赖固定 35 份文件；官方 ZIP 和解压后的服务器/DLL/包内许可文件均绑定大小与 SHA-256。使用已有 `yauzl` 流式解压，只写入固定清单；拒绝越界路径、符号链接、加密、重复名称、大小/哈希不符及超限内容。完整校验后原子发布，获取二进制时重新校验并持有租约；使用中不能删除，损坏后可从已缓存 ZIP 离线修复。准备任务可共享，每个调用方独立取消，最后一个调用方取消后才终止准备；重试等待旧任务清理完毕，退出后不再返回新的二进制租约。`node tests/llama-runtime-store.cjs` 覆盖解压边界，`--runtime` 验证实际 CPU/CUDA 包的离线安装、版本/设备加载、共享取消、独立进度、租约、损坏修复和清理。`node scripts/prepare-llama-runtime-benchmark.mjs --backend all` 只验证既有 ZIP，显式加 `--prepare` 才允许下载。

后台推理由 `native/inference-host.h` 和 `LlamaSession` 管理：Windows Job Object 限制单进程和整组提交内存，超过预算或父宿主退出时终止整组进程；控制消息与模型日志分开，进程身份使用 PID 与创建时间，取消等待退出后才释放文件租约。服务只监听 127.0.0.1，使用随机端口和每次会话独立密钥；确认自身监听日志后再请求就绪状态，采用 `node:http` 发送图片，不跟随重定向。b11588 HTTP 路线需明确使用 `--no-jinja --chat-template deepseek-ocr`；保留 v2 的 DRY 参数。`node tests/inference-host.cjs` 验证参数、控制管道、硬预算与父进程退出；`node tests/llama-session.cjs` 覆盖协议边界、超时、取消、启动/关闭竞争与私有目录清理，`--runtime` 验证 v1/v2 的 CPU/CUDA 共 12 次英文、相同图片复用及深色中英/邮箱换图识别，全部离线。

`LlamaRunner` 通过共享本地调度器持有 GGUF 和运行包租约，按模型版本、设备 LUID/CUDA ordinal、预算复用服务；模型/预算/文件元数据变化或其他引擎接管前卸载，空闲后释放。入队冻结原图与设置，获取大权重时支持取消校验；只有自动模式的 GPU 加载/运行/预算/超时错误才尝试同一模型 CPU，强制 GPU 和协议/完整性错误直接保留错误。清理失败时保留租约，后续可重试；不在退出未确认时删除权重。`node tests/llama-runner.cjs` 覆盖缓存、快照、排队取消、同模型回退和清理失败；`--runtime` 使用真实固定 GGUF 与 CPU/CUDA 包验证租约、换图复用、跨引擎卸载、主动取消、GPU 硬预算触发后的 CPU 识别及删除。当前 `Free OCR.` 输出只生成文字文档，不伪造图上文字框或模型置信度；图上几何仍未验收，模型详情明确显示暂不支持图上选字；文字识别窗口主流程已完成实机验收。结果保存在 `work/current/capture-reconstruction/deepseek/native-session-results.json` 和对应 `native-*-real.log`。

### 3.3 图片文字数据与选择交互

统一输出 `document → blocks → lines → tokens`，每个节点有稳定 ID、阅读顺序、原图像素坐标、四边形、文字与可选置信度；同时记录引擎/模型版本、图片哈希、预处理到原图的变换。中文尽量支持字级、英文支持词内选择；优先采用引擎词框与识别对齐信息，不能把整行平均分宽后宣称精确字框。近似位置单独标记并实测。

交互设计：

- 原图是主工作区，图上直接拖选；双击词/短语、三击行、跨行拖选，选区遵循阅读顺序而非单纯矩形相交。
- 选择层使用几何高亮和透明可访问文本层；提供 Ctrl+C、Ctrl+A、Shift 扩选与键盘操作。区分选字、框选局部识别、拖动画布，按住空格平移。
- 缩放、平移、旋转、适应窗口、不同 DPI 都使用同一坐标变换；视觉高亮和实际复制范围保持一致。
- 选中后浮出紧凑操作条：复制、翻译、重新识别。右侧可展开结果/校正面板，选择与文字列表联动；修改文字不擅自移动原图坐标。
- 长图片采用分块识别和可视区渲染，块边重叠去重、保留全图坐标，解决现有最长边 8192/1200 万像素对长图的限制；大图不一次解码和推理全部内容。
- 选择层作为共享组件接入独立 OCR 窗口、图片预览和截图编辑器；用户在图片上点击“识别文字”即可进入选字模式，沿用当前图片、缩放和位置，不强制跳到另一个纯文本窗口。识别按需运行，网络增强由用户选择。

验收同时看识别字符错误率、选字位置、阅读顺序、冷/热耗时、峰值内存和取消响应。现有 `confidence` 不能直接与其他引擎数值比较。

默认引擎必须在中英屏幕截图主样本上优于当前 Tesseract，并检查每类样本是否出现明显退化；具体阈值在 A 阶段测量后冻结。v6 未通过时选择更合适的 v5 配置或继续优化，不为追新直接替换。

首批实现保留 Tesseract 的真实符号框，产出带图片 SHA-256、引擎/模型版本与坐标变换的 `TextDocument`；字符文字与词不匹配或没有字形框时保留实际词框，不均分伪造。共享选择层已接入独立识别窗口，支持跨行、词内、词/行选择、键盘复制扩选与缩放旋转；单次拖选期间冻结变换，避免 ResizeObserver 或工具栏换行改变取点坐标。只为可视区建立文字节点，过密视图要求放大但允许全选复制。原图翻译、其他模型预设、自由全文编辑后的几何重对齐仍按后续批次推进；按词校正已保留原词范围并联动复制/全文选择，自由全文编辑仍关闭旧坐标选择层以防复制过期文字。

### 4.2 原图翻译

默认管线：冻结原图 → OCR/段落归并 → 分段翻译 → 生成文字掩膜 → 背景处理 → 按原区域排译文 → 可编辑结果。

- 先覆盖文档、聊天截图和网页的水平文字：同色/简单渐变背景按区域估计颜色处理，保留图片和装饰。
- 复杂背景评估项目现有 MI-GAN 修复能力是否适合小字掩膜，不直接承诺无痕；掩膜只覆盖文字笔画，避免抹掉图表/线条。不合适时明确使用可读底板，并允许切回原图。
- 按块拟合字号、行距、换行和对齐；译文变长时给出溢出提示/展开区域，不能无下限缩小字体或遮盖相邻块。竖排、旋转、混合方向列入专项验收。
- 工具条：原文/译文切换、目标语言、服务、重新翻译、复制/保存；支持按住查看原图，点击译文块修正。编辑器保留原图、文字层和翻译版本，导出时再合成。
- 腾讯已有返回翻译图片的专用接口，可作为可选快速来源，但其输出为 JPG；是否同时保留可编辑分段信息另行核对，不能默认与本地可编辑翻译层等价。[官方说明](https://cloud.tencent.com/document/product/551/118482)

旧配置迁移：已有 chat 连接转成 AI Profile 引用，Azure 转成专用翻译连接；按协议/地址/模型及主进程中的凭据匹配去重，不能只按名字合并。旧完整 endpoint 与 AI baseUrl 语义不同，需验证转换。成功保存、回读和备份兼容验证后才清理旧记录；解密失败保留原记录并提示重新配置。

## 5. 长截图：手动与自动共用一条采集管线

### 5.1 调研判断

长截图没有通吃全部应用的滚动接口。ShareX 的公开方案是选窗口/区域、滚动、采帧和图像匹配；其官方文档明确指出固定侧栏、页头页脚、动画和 hover 效果会干扰拼接。[ShareX 长截图](https://getsharex.com/docs/scrolling-screenshot)

微信/QQ 的内部算法没有在本轮找到可核实的官方实现资料，采用用户描述的交互作为目标，不声称复制其内部算法。浏览器整页协议只适用于有权限控制的浏览器页面，不能替代任意桌面软件选区截图。

### 5.2 使用流程与窗口布局

1. 普通区域截图完成框选后，工具栏出现“长截图”；沿用当前显示器和选区，进入时不要求再选一次。多窗口合成、自由形状等不适用来源不显示该按钮。
2. 默认“手动滚动”：用户滚鼠标、触控板或拖动滚动条，系统自动检测稳定帧并拼接；无需每滚一屏再点采集。
3. “自动滚动”：确认目标窗口和滚动点后开始；可以随时暂停、改成手动并继续已有结果。不能因为操作栏获得焦点就使自动模式无法开始。
4. 选区外侧放紧凑浮动条：模式、暂停/继续、撤销、完成、取消；一侧是可折叠的窄缩略长图，显示当前视口位置和新增区域。避免现有截图中左侧超长预览挤压内容。
5. 完成后进入统一图片编辑器；拼接纠错、裁剪、标注、复制、保存都有明确入口。高级固定栏排除/匹配参数放入设置面板，默认不要求填写像素偏移。

### 5.3 引擎重构

状态分离为“准备/手动运行/自动运行/暂停/待确认/完成”，用户模式与匹配状态分开。两种模式共用原生采集、稳定检测、变化检测、匹配、去重和增量结果。

- WGC 采集会话持续复用；评估原始像素通道，避免每帧在主进程反复 PNG 编解码。工作线程处理匹配，界面仅接收降采样预览和状态。
- 自动滚动步长根据上次实际位移调整，保留足够重叠；等待页面稳定和新增内容，而不是仅依靠当前 140ms 等待和 250ms 调度。慢加载/平滑滚动允许延迟，重复帧不是立即到底。
- 多尺度位移搜索与局部一致性验证；弱纹理、重复列表、动态广告应降低匹配置信度。只做必要平移，不能用透视拉伸“拼上”文字。
- 固定页头页尾保留一次，匹配时排除固定区域/侧栏/滚动条；自动检测提供可视化修正。只有局部动画时屏蔽该区域，不能全图一直等待。
- 手动快速滚动导致无重叠时暂停追加，保留已拼结果，提示滚回一段找回衔接；反向滚动用于定位恢复，不重复追加。低置信度帧不自动硬拼。
- 自动输入只作用于已确认目标；目标关闭、遮挡或失去可用滚动条件时暂停，不把滚轮发送给其他程序。触控板、拖动滚动条也能通过图像变化采集。
- 平铺条带/磁盘暂存处理长图，遵守内存、磁盘和最大输出限制；达到上限时允许保存已有内容。取消/失败仅回收本会话自有缓存。
- 窗口边框、浮动条、预览自身排除采集，无法排除时隐藏采样；不假设所有远程桌面都支持捕获排除。不同 DPI、负坐标和显示器变化单独处理。

## 6. 多窗口快照与表格识别删除

多窗口先做最小复现：选择 2～4 个窗口 → 截图 → 移动/缩放/最小化/关闭源窗口 → 标注 → 保存，同时分别测试“不刷新”和“主动刷新”，记录会话 ID、版本、错误分支、HWND/PID、前后尺寸和显示器签名。不记录图片内容或密钥。

设计改为 `CaptureSnapshot` 持有冻结图层、尺寸、布局和版本；源窗口身份只用于采集/刷新。保存、复制、OCR 和编辑使用这个快照。源关闭或显示器重排不应使已取得的离线像素无法导出；贴图定位等实时操作单独降级。

首批实现已使用冻结元数据和逐窗口采集边界；取得的图层不再因其他源窗口后续变化被丢弃。真实双窗口测试复现的“图片原图已改变”来自组合截图缺失 `composition: windows`，导致归档把首图当作整个组合原图；修复后组合原图单独编码并随工程归档。刷新采用候选版本 → 界面解码 → 确认提交，两端解码/采集失败都保留旧图；尺寸或任一图层布局变化时保留旧图与标注并提示重新采集。显示器改变只影响实时区域操作与贴图定位，图片导出继续使用快照。此结论不等于已复现历史用户环境的全部报错。

首次采集仍需检查 HWND/PID 和帧有效性，防止复用错误窗口；位置变化与尺寸变化分开处理，可有限重试重新定版。刷新重新生成候选快照，成功后原子替换，失败保留旧快照。布局变大不再直接判定原快照失效；若影响已有标注，保留旧版并由用户确认重采，不能静默错位。保存对话框打开、失焦、同名窗口、混合 DPI、透明窗口都纳入回归。

删除“表格识别”涉及识别窗口页签/按钮、截图流程入口、IPC/preload/types、表格重建/校正/复制导出实现、测试和用户说明；旧配置中的动作明确提示已移除，不静默改成另一种功能。仅删除识别子系统专属代码，不删除 Excel/CSV/工作簿预览、JSON 表格展示等独立能力。

首批源码已移除上述表格专属实现和页面，旧 `table` 模式请求明确拒绝；现有截图输出动作没有表格专属动作或持久化表格配置，无需静默替换配置。独立工作簿功能与其依赖保留，普通 OCR 使用原有文字版面识别。识别窗口回归检查已移除页签和桥接，并继续验证实际中英文 OCR、复制、翻译和公式；目录包/安装版的最终核验仍随 F 收口。

## 7. 公式识别方案

| 方案 | 调研事实与取舍 |
| --- | --- |
| SimpleTex | 提供专用公式 API，标准 `/api/latex_ocr`、轻量 `/api/latex_ocr_turbo`，返回 LaTeX 和置信度。适合作为云端专用来源。官网演示不是离线模型下载，本轮未找到官方可下载权重；文档计费/赠送说明存在不同口径，实施时以账户控制台为准，不在产品中写死免费额度。[官方 API](https://doc.simpletex.cn/zh/api/) |
| PP-FormulaNet_plus | 官方有 S/M/L。文档中 S 权重约 248 MB，M 约 592 MB；S 偏英文公式，M/L 增强中文公式。适合优先做本地候选。CPU、Windows 推理与转换路径必须原型验证，不能把 Paddle 推理模型直接当作现成 ONNX 包。[模型文档](https://www.paddleocr.ai/main/en/version3.x/module_usage/formula_recognition.html) |
| UniMERNet | 专门图像到 LaTeX，仓库提供 tiny/small/base，下载说明约 441 MB/773 MB/1.3 GB；官方采用 Python/PyTorch 环境。作为复杂、截图和手写公式的比较候选，默认安装器不捆绑整套运行环境。[官方仓库](https://github.com/opendatalab/UniMERNet) |
| pix2tex / LaTeX-OCR | 专门方程图片转 LaTeX，MIT 仓库，作为轻量方案与识别质量基准；不能推断其覆盖全部中文、手写和复杂多行公式。[官方仓库](https://github.com/lukas-blecher/LaTeX-OCR) |
| 现有 AI 视觉服务 | 复用已有 Profile/模型、图片传输、密钥和取消；提示模型只转写不求解。提供图片裁剪和结果核对，不能伪造模型置信度。 |

先打通现有 AI 视觉任务 + SimpleTex 专用适配器，同时完成本地模型家族及各尺寸的 CPU/GPU 适配矩阵和代表性实测，再分批接入模型管理。ONNX 转换不可靠的型号使用经过验证的独立推理运行包，按需安装，也允许连接用户已有的本机服务；不把大型 Python 运行环境强制加入所有用户的安装器。完整本地、多模型、多尺寸能力均是明确交付项，不能只提供云端或一个默认模型后宣布完成。

结果界面统一为裁剪原图 + 可编辑 LaTeX + KaTeX 预览；支持复制 LaTeX、复制公式图片、导出 SVG/PNG。矩阵、分段、上下标、多行和手写样本分别验收。KaTeX 不支持的合法语法保留原文并提示，不能丢弃或执行任意 TeX/外部命令。

### 验收样本与指标

- OCR：至少 60 张分层样本，覆盖中英混排、小字、深色、低对比、旋转、双栏、聊天、代码、日文和超长图；人工标注文字及关键几何区域。记录字符错误率、漏检/错检和选择定位误差。
- 公式：至少 40 张，含打印、截图、手写、分式、矩阵、分段、多行与中文夹杂；检查符号和结构正确性，不以 LaTeX 字符串逐字相同作为唯一标准。上游 CDM 可作参考。
- 翻译：至少 30 张文档/聊天/网页/复杂背景样本；分段一致性、可读性、溢出、非文字区域保留和原图切换人工验收。无账号的服务只做协议桩测试，不能标为真实服务验证通过。
- 长截图：浏览器、资源管理器、聊天、PDF、不同 UI 框架，含懒加载、固定栏、动画、重复行、反向/快速滚动、拖动滚动条、触控板、多屏缩放；至少 20 个脚本/人工场景，核对缺行、重复和可恢复性。
- 多窗口：至少 15 个状态场景，覆盖源窗口移动/关闭/缩放、同名 HWND/PID 身份、保存对话框失焦、主动刷新失败、显示器变化与混合 DPI。
- 冷启动、热运行、峰值内存、模型下载/取消、请求超时、窗口关闭和版本升级均记录；具体耗时门槛由 A 阶段实测冻结，不先承诺未经验证的毫秒数或准确率。
- 每个本地模型/尺寸至少验证声明支持的 CPU/GPU 后端，记录显卡、驱动、运行包和精度；覆盖双显卡选择、显存不足、模型共存切换、设备丢失和 CPU 回退。质量与性能结果按具体型号分列，不把某个尺寸的成绩套给全家族。

## 9. 尚未验证的关键事项

PP-OCRv6 在目标 Windows CPU 和已有 ONNX Runtime 下的实际耗时及前后处理兼容；中文细粒度选择定位；本地公式的自回归解码/转换与权重许可；现有 Codex 和各服务实际视觉模型能力；复杂背景擦字质量；真实长截图目标的滚动注入和遮挡行为；多窗口报错的实际发生路径。以上是实施前的验证门槛，不是已经解决的结论。
