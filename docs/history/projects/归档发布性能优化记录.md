# 归档发布性能优化记录

本阶段优化“解压到当前位置”的逐文件发布。基线为 `d9a6dfa31d5aaae1b5b5fa199f40b7d3cfc5e7df`，已包含上一阶段的 ZIP 目录复用；优化版为本记录所在提交，原生组件、源码哈希和原始分组见[测量数据](../measurements/archive-publish.json)。此前的小文件阶段记录保留当时结果。

## 原因与修改

同一十万文件真实服务流程中，独立诊断构建测得原生发布 279.003 秒，其中 100,000 次申请内容读取权限的文件打开累计 235.023 秒。仅改为属性读取加删除权限后，诊断发布为 58.134 秒；两个流程的全部输出均通过核对。一万文件的初步四次交替测试范围重叠，没有显示稳定收益，因此保留十万规模验证。API 时长用于定位，不足以确定底层驱动、杀毒软件或物理设备原因。

发布、自动撤销和提交后备份清理只检查文件元数据，再通过句柄移动或删除文件，不读取有效载荷。五处句柄改为 `FILE_READ_ATTRIBUTES | DELETE`；显式崩溃恢复和恢复副本清理的三处句柄同步调整。恢复日志仍以 `GENERIC_READ | DELETE` 打开，因为需要读取和验证记录。

保持 `FILE_SHARE_READ`、身份及时间/尺寸核对、拒绝链接和覆盖式移动、日志持久化与确认握手。请求删除权限仍参与共享冲突判断；实际 Windows 测试确认兼容读取可用，写入、删除及不兼容既有句柄仍会阻止操作。没有减少日志落盘次数或跳过 CRC/认证、来源、扫描和风险检查。

## 正式测量

Windows 11 build 26200、AMD Ryzen 9 7940HX、D 盘 NTFS，继承开发进程权限，未提权。线程 2、共享内存预算 1,024 MiB。复用同一生成 ZIP：100,000 个非空 Deflate 文件、1,000 个交错分支、中文路径、ZIP64 条目数量；每文件 256 字节，总输出 25,600,000 字节，归档 18,710,833 字节，SHA-256 `8fa66269821f41ffdbc4dde67aca9cdac24f2587b7884b2eb288d690946a552b`。这是确定性合成小文件，不代表真实文件熵或大文件吞吐。

正式程序不含诊断计时，按基线、优化、基线、优化交替完成四轮真实 `ArchiveService` 请求，每次新建目标。十万项正常触发风险预检，确认前不写输出；确认绑定归档版本，限制 64 GiB / 30 分钟。来源传播开启，生成源无 Zone.Identifier，AMSI 关闭。没有清空系统缓存或冻结背景负载，测量期间没有同时构建或运行重负载测试。

四轮共 400,000 个输出分别核对长度和 SHA-256，既有 `keep.txt` 保留，未留下暂存或恢复目录。核对和删除测试输出时间另计。以下时间为每版两轮中位数，内存为每版最大 OS 峰值；进程私有内存另按 20 ms 采样，CPU 和逻辑 I/O 保存在数据文件。逻辑 I/O 不代表物理磁盘吞吐，Node 内存仅为请求完成快照。

完整请求中位数减少 71.6%，原生发布减少 80.7%。基线完整请求两轮为 387.412 / 391.658 秒，优化后为 102.951 / 118.486 秒；发布分别为 339.649 / 348.209 和 58.039 / 74.563 秒。

上一阶段的发布中位数约 407 秒，本阶段使用新做的交替基线对照，避免把不同时间的缓存与背景负载变化全部归为代码收益。诊断构建的数字也不混入正式对照。每版两次样本不构成跨机器统计保证。

## 回归与复现

权限测试严格编译通过，覆盖原权限/最小权限及普通/只读文件的四种组合，包括兼容读取、写入/删除冲突、既有句柄冲突、身份和属性保持、目标碰撞、句柄移动/删除及释放。真实 ACL 仅拒绝当前用户的内容读取，验证发布和旧备份删除、自动撤销、崩溃还原及新副本清理、提交后清理四组流程；额外拒绝恢复日志读取时，还原和清理均拒绝处理并保留资料。

完整应用构建、最终原生重建通过。发布、日志、恢复、还原、清理、来源、扫描、认证、原生基础、格式、CLI 十一组回归通过；恢复三处权限补齐后，前五组和实际 ACL 测试再次通过。诊断工具独立构建的一万项流程通过严格编译和全部内容核对。文档检查通过。

```powershell
npm run build
python tests/archive-small-files-benchmark.py
npm run test:archive-publish-access
node tests/archive-small-files-benchmark.cjs --label current --mode here --repeat 2
# 可选诊断：先完成当前源码构建，单独生成带 API 计时的辅助程序
node tests/archive-publish-profile.cjs --label diagnostic
```

前后对照用 `--helper-dir` 指向独立保存的辅助程序、预算 DLL 和 7-Zip DLL；历史基线须从指定提交构建，不混用旧对象文件。诊断脚本只替换隔离构建的发布对象，并要求其他原生对象与当前源码一致；不修改产品源码或正式程序。原始测量在 `work/current/archive-publish-perf/`，精选验证与组件对应关系在 `verification/archive-publish-perf/latest.json`。

物理 I/O、其他格式和桌面/安装版小文件流程、超大固实包、混合并发、慢盘及网络盘仍待验收；本阶段只确认上述 NTFS 合成数据的发布收益。
