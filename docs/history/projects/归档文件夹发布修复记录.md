# 归档文件夹发布修复记录

RAR 组合验收期间，既有回归曾在新文件夹最终改名时遇到一次 Windows `EPERM`，唯一重试通过，未取得原始占用来源。此次用真实 Windows 共享句柄复现同类短暂占用失败，修复新文件夹与智能解压的目录提交。没有把受控实验的 `EBUSY` 归因为原始 `EPERM` 的确定原因。

## 行为与边界

原流程在独立引擎完成提取后，只调用一次目录改名；即使占用将在 500 ms 后释放，也立即失败。新 `archive-folder-publish.ts` 仅在 Windows 的 `EPERM/EACCES/EBUSY` 上短时等待：最多七次尝试，六次间隔 50/100/200/400/500/500 ms，总间隔 1.75 s。不存在、格式不符等其他错误直接返回，不持续重试或修改权限。

每次尝试前通过 `lstat` 检查目标，已出现的目录、文件或链接都停止提交；正常预先存在的名称仍沿用原序号规则。智能解压单个文件继续使用硬链接发布。最终提交期间保持原有不可取消状态，提交之前仍可取消。持续占用及同名竞争转换为明确的写入失败提示；提取暂存清理增加有限重试，仍失败时记录准确的私有暂存路径和错误码，便于定位，没有将未清理暂存当作已发布结果。

## 验证

`tests/archive-folder-lock.cpp` 在独立进程里持有不共享删除权限的真实 Windows 读取句柄。测试执行真实原生解压，只在返回服务、尚未提交时取得句柄；产品中没有测试开关。原始提交 `1535b2d` 的普通/智能目录两种基线均在 0–1 ms 返回 `EBUSY`，早于计划的 500 ms 释放。基线日志保留在 `work/current/archive-folder-publish/baseline.log`。

`npm run test:archive-folder-publish` 覆盖八个场景：

- 普通与智能目录的占用在 500 ms 释放后成功发布，输出内容哈希与来源一致。
- 持续占用在有限等待及清理尝试后返回写入错误，没有结果目录；无法清理的私有暂存有诊断记录。
- 等待中创建同名目录及文件，已有内容保持完整，本次失败。
- 提交前可取消且没有输出；最终提交等待中取消被拒绝，随后正常完成。
- 预先存在的同名目录保持原内容，新结果选择序号名称。
- 智能解压单文件保持硬链接发布及已有同名文件保护。
- 不可重试的不存在错误立即返回。

完整应用构建通过；RAR 400 项组合、既有 RAR、四个 RAR 桌面流程、当前位置事务发布、任务与真实 CLI 回归通过。源文件、组件、测试及日志哈希与本记录所在提交的对应关系在 `verification/archive-folder-publish/latest.json`，工作日志保留在 `work/current/archive-folder-publish/`。

此修复不代表已证明原始一次 `EPERM` 的外部来源，也不证明网络盘、任意驱动或所有权限差异均已覆盖。持续占用的结果仍需用户关闭占用程序或更换目标；实际编辑器、拖拽、安装及其余归档验收继续按计划推进。
