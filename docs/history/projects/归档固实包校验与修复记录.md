# 归档固实包校验与修复记录

本阶段用 4.125 GiB 单固实块验证 7Z，修复两处实际问题：只选包尾项目时，解码前置文件被误计为完成项目，先显示 `1 / 1`、结束显示 `2 / 1`；原生解压及 OLE 内容读取只在选中输出处检查时间上限，跳过前置内容期间不能及时停止。服务进程原有定时器已正常保护普通解压，本阶段保留它并补齐原生检查。

实现为本记录所在提交，完整测量在[数据记录](measurements/archive-solid.json)，组件及验证绑定在 `verification/archive-solid/latest.json`；原始日志、冻结组件和样本在 `work/current/archive-solid/`。基线提交为 `ab5aaf8`。

## 实现

`native/archive/sevenzip.cpp` 根据 SDK 的操作模式，仅统计实际提取的选中项或完整性测试项。跳过前缀仍执行原有 CRC、数据结果和长度检查，不能因为未计进度而忽略损坏。

解码进度及获取流时检查 `ExtractionSpace::write(0)`，使没有选中输出的固实前缀也受时间与空间检查约束。零字节检查不把跳过数据计入展开量，选中的 1 KiB 项仍可在 1 KiB 输出预算内读取；用户取消和资源失败继续沿用现有机制。

## 数据与方法

外部官方 7-Zip 25.01 生成 LZMA2、32 MiB 字典、单线程、一个固实块，完整性检查通过。三个文件为 128 MiB、4 GiB + 4096 字节、1 KiB，总计 4,429,190,144 字节，归档 687,431 字节。每 MiB 内重复固定的 32 KiB SHA-256 数据，头部计数变化；并非纯零文件，也不代表现实文件熵。生成时独立流式计算三个 SHA-256，未在内存中分配整个文件。

测试机为 Ryzen 9 7940HX，系统报告约 15.2 GiB 内存，D 盘 NTFS；原生解压指定单线程与 256 MiB 进程预算。基线和修复版独立冻结，每次使用新的输出目录，完成后流式核对输出哈希并限定目录清理。测量期间不运行构建或其他测试；系统后台负载和 OS 缓存未隔离。

两版各三轮包尾及完整输出，初轮还验证首项、服务时间上限与取消；顺序为 A/B/B/A/B/A，A 为基线。共核对 26 个输出哈希。Windows 进程观察器记录峰值提交内存、CPU 与逻辑 I/O，不将逻辑 I/O 当作物理盘吞吐。

## 结果

| 场景 | 基线 | 修复后 |
| --- | --- | --- |
| 首项解压，128 MiB | 138 ms | 136 ms |
| 包尾 1 KiB，三轮范围 | 2227–2269 ms | 2193–2268 ms |
| 包尾进度 | 约 98 ms 提前报 1/1，结束 2/1 | 实际选中项完成时报告 1/1 |
| 原生解压，100 ms 时间上限 | 2239 ms 才停止 | 137 ms 停止 |
| 原生 OLE 读取，100 ms 时间上限 | 2174 ms 才停止 | 151 ms 停止 |
| 服务层 100 ms 时间上限 | 131 ms 停止并清理 | 129 ms 停止并清理 |
| 服务层发出取消后的返回 | 约 12 ms | 约 12 ms |
| 原生进程峰值提交内存 | 约 35 MiB | 约 35 MiB |

时间上限测量包含启动、解码回调及收尾开销，不是硬实时保证；取消返回测量也包含进程观察器的少量收尾开销。完整输出壁钟耗时基线 3.54–14.98 s、修复版 3.56–3.69 s，但 CPU 时间和逻辑 I/O 接近，存在明显非 CPU 等待波动；原因未定位，不把差异解释为本次吞吐提升。包尾时间说明同一固实块内的前置解码成本，并不表示程序还提取了未选文件。

另用 One 在 256 MiB 预算下创建包含同样三个文件的 7Z，耗时约 17.58 s，外部 7-Zip 完整性检查通过；One 完整解压约 3.54 s，三个完整 SHA-256 一致，确认超过 4 GiB 的单文件创建与读取。本阶段大样本合计 29 个输出哈希核对。

## 回归与复现

`npm run test:archive-solid` 离线生成 544 MiB + 1 KiB 的单块样本，验证选中项计数、原生及 OLE 前缀时间上限、仅选中内容的字节预算、完整哈希、取消清理和损坏前置数据拒绝发布。显式选择 1024 MiB 固实范围；引擎的 `solid/on` 会按字典等配置自动决定分块，不能假定它始终为整个包单块。

`npm run test:archive-solid-ui` 使用本阶段大样本，验证真实桌面中的包尾进度、停止按钮、清理与重试提取，并核对 1 KiB 输出及界面计数。格式、LHA、RAR、RAR 400 项组合、原生、详情、拖出、空间、风险、资源、压缩选项与真实 CLI 回归及完整构建通过。

开发者可用 `node tests/archive-solid-fixture.cjs <官方7z.exe绝对路径> <新工作目录>` 生成数据并冻结当前组件。生成器拒绝覆盖现有输入和组件；创建时间、工具版本等使新归档哈希可能变化，不能冒用旧样本哈希。将待比较组件放在工作目录的 `baseline/native` 和 `fixed/native`，通过 `tests/archive-solid-benchmark.cjs --fixture <目录> --label <版本> --report <新报告名>` 测量；报告也拒绝覆盖。当前测量使用的原始生成脚本另存为 `prepare-used.cjs`。

其他字典、方法、加密、多块、多卷及真实文件集合，完整输出等待波动的归因，混合任务、慢盘/网络盘和真实系统入口仍待推进。此记录完成本机这一组压力与修复验收，不代表全部归档性能目标达成。
